Escribass

Six plates showing the desktop shell implied by docs/specs.md §9, drawn against the canonical demo from §18.2: change the bass line in bar 17, re-render, everything else identical.

The same pending edit runs through every plate — proposed in the AI panel, unapplied in the arrangement, dashed in the piano roll, waiting at the head of the patch log. Nothing here is built. M0 ships the schema, core and tool API only; this is what the tool API will eventually be driving.

What the spec dictates

  • Which views exist — arrangement, piano roll, mixer, instrument/effect editors, code views, AI panel, history (§9).
  • The AI panel shows a diff before applying, with apply / reject / edit (§9, §5).
  • All seven views are projections of one model; none holds its own state (§2.1).
  • Ticks, sections, provenance, seeds, pinned refs are model fields, so they are displayable everywhere (§4).

What I invented here

  • Every layout decision. Panel placement, split ratios, the tab strip, the right-hand dock — §9 lists views, not composition.
  • Plate 6 as a dedicated screen. §11 and §18.2 require the capability; nothing says it's a view rather than a test report.
  • Colour as provenance. Teal for model-authored, amber for pending. Reasonable, but it's a call, not a requirement.
  • The pending clip drawn in the timeline. A defensible reading of "shows the diff", not a stated one.

Scope check

None of this is M0. M0 is schema/song.proto, the Rust core, the SongTools service with dry_run, its MCP surface, and the determinism suite. The value of drawing the shell first is that it fixes what the tool API has to be able to answer: every panel above is a read of the model, and every control is one tool call. If a panel here needs data the schema can't express, that's a schema gap worth finding before the proto is written — not after.
